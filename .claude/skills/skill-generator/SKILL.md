## Purpose

解决的核心问题：手工编写 skill 体系时，容易出现职责重叠、流程断裂、约定不一致等问题，且缺乏系统性的质量检验手段。

本 skill 提供两种工作模式：

- **生成模式**：基于参考文档或用户描述，沟通后生成一组新 skill，并自动进入多轮评审
- **评审模式**：对已有 skill（修改后）直接执行多角色评审，输出优化建议

## 评审角色池

执行时用户可**选择参与角色**（默认全选），不强制每次所有角色参与。

| # | 角色 | 评审关注点 |
|---|------|-----------|
| 1 | 资深 AI 提示词工程师 | prompt 结构是否清晰、指令是否无歧义、是否有幻觉诱导风险、上下文控制是否合理 |
| 2 | 资深产品经理 | 用户场景覆盖是否完整、流程是否顺畅、输出物是否满足业务目标 |
| 3 | 资深项目经理 | skill 间依赖关系是否清晰、交付物定义是否明确、中断恢复机制是否可行 |
| 4 | 资深交互设计 | 人机交互流程是否自然、信息密度是否合理、用户认知负担是否可控 |
| 5 | 资深前端开发 | 涉及 UI/原型类 skill 时，产出物是否可实现、交互描述是否落地 |
| 6 | 资深后端开发 | 涉及数据/接口类 skill 时，数据流描述是否合理、接口约定是否可执行 |
| 7 | 资深架构师 | skill 体系职责边界是否清晰、模块化程度、扩展性、数据流向是否合理 |
| 8 | 运营数据分析 | 是否有效果度量手段、产出物是否支撑数据驱动决策 |

| 10 | 技术文档工程师 | 文档结构是否一致、术语是否统一、是否有歧义表述、可读性与可维护性 |

## 角色选择交互规范

进入评审环节时，必须向用户展示完整的角色列表供选择，格式如下：

```
请选择参与本次评审的角色（输入编号，多个用逗号分隔，或输入"全选"）：

 1. AI 提示词工程师 — prompt 结构、指令歧义、幻觉风险
 2. 产品经理 — 场景覆盖、流程顺畅、输出物价值
 3. 项目经理 — 依赖关系、交付物定义、中断恢复
 4. 交互设计 — 人机交互、信息密度、认知负担
 5. 前端开发 — UI/原型可实现性、交互落地
 6. 后端开发 — 数据流、接口约定可执行性
 7. 架构师 — 职责边界、模块化、扩展性
 8. 运营数据分析 — 效果度量、数据驱动
 9. QA/测试工程师 — 验收标准、可验证性、边界覆盖
10. 技术文档工程师 — 结构一致、术语统一、可读性

推荐组合：
  A) 全选（10 个角色，适合最终交付前的完整评审）
  B) 核心组合：1+2+7+10（适合日常迭代评审）
  C) 自定义选择
```

**关键要求**：
- 不可只给"全选/核心/自定义"三个选项而不展示角色列表。用户必须能看到每个角色的编号和关注点后再做选择。
- 若执行环境支持结构化选择工具（如 AskUserQuestion），可使用工具实现，但必须在选项描述中展示所有角色编号及关注点，不可省略角色列表。

## 模式一：生成模式

### Phase 0：状态检查与中断恢复

每次启动时，先检查是否存在上次未完成的工作：

1. **检查输出目录**：查看用户指定的输出目录下是否已有产物（架构图、已生成的 skill 文件、评审报告等）
2. **判断执行状态**：
   - 无任何产物 → 从 Phase 1 开始
   - 有架构图/清单表但无 skill 文件 → 可能在 Phase 3 前中断
   - 有部分 skill 文件但未全部生成 → Phase 3 进行中中断
   - 有全部 skill 文件但无评审结果 → Phase 4 前中断
   - 有评审结果但无优化执行记录 → Phase 5/6 前中断
3. **向用户展示状态判断**并提供选择：
   - 继续：从中断点继续执行
   - 重新开始：从 Phase 1 重新执行
   - 指定环节：跳转到用户指定的 Phase

### Phase 1：需求理解与范围确认

1. **获取输入**：用户可通过以下任一方式提供需求：
   - 提供参考文档路径（需求文档、流程说明、现有 skill 等）
   - 直接描述需求（口头说明想要什么样的 skill 体系）
   - 两者结合（提供文档 + 补充说明）
2. **分析输入**：提取以下信息：
   - 业务领域与核心场景
   - 涉及的角色和流程
   - 潜在的 skill 拆分点
3. **与用户沟通确认**：
   - 需要生成哪些 skill（名称 + 一句话定位）
   - 各 skill 之间的依赖/调用关系
   - 是否需要一个 conventions 类 skill（统一约定文件，各 skill 引用同一套规范，避免每个 skill 各自定义导致不一致）
   - 是否需要 init 类 skill（首次使用时引导用户完成路径、格式等配置，使 skill 适配用户的项目环境）
4. **确认生成的 skill 中涉及的输出目录**：
   - 生成的 skill 在使用过程中会产出哪些文档（如需求文档、评审报告、Baseline 等）
   - 这些文档的默认保存位置应该设为哪里
   - 确认后将目录配置写入对应 skill 的约定中

### Phase 2：Skill 体系设计

1. **输出 skill 架构图**：用 Mermaid 展示各 skill 的关系（依赖、调用、数据流向）
2. **输出 skill 清单表**：

```
| # | skill 名称 | 类型 | 一句话定位 | 输入 | 输出 | 依赖 |
|---|-----------|------|-----------|------|------|------|
```

3. **与用户确认架构**：用户确认或调整后进入生成阶段

### Phase 3：逐个生成 Skill

按依赖顺序逐个生成（被依赖的先生成）：

1. conventions/基础约定类 skill 最先生成
2. 每个 skill 必须包含以下标准结构（参照用户已有 skill 格式）：
   - **frontmatter**：name / description（含触发词）/ type / theme
   - **Purpose**：解决什么问题，核心理念
   - **输入**：skill 接受哪些输入
   - **输出目录规范**：产出物的存放位置
   - **工作流程**：分 Phase/Step 的具体执行步骤
   - **全局约束**（可选）：执行边界、禁止行为、特殊规则等
3. 每个 skill 生成后，简要展示核心结构（Purpose + 工作流程步骤概览）
4. 用户可逐个确认或批量确认
5. 所有 skill 生成完毕后，进入评审阶段

### Phase 4：多角色评审

> 进入评审前，按「角色选择交互规范」展示完整角色列表，由用户选择参与角色。

#### 评审降级策略

- **选定角色 ≥ 3**：执行完整三轮（独立 → 交叉 → 自我修正）
- **选定角色 = 2**：执行两轮（独立 → 交叉评审后直接输出最终建议，跳过第三轮）
- **选定角色 = 1**：仅执行第一轮独立评审，直接从评审意见输出优化建议，跳过第二、三轮

#### 第一轮：独立评审

每个选定角色**逐个**审查待评审的 skill。每个角色从 skill 原文出发分析，可参照用户已有 skill 体系作为风格/约定基准，但不引用其他角色在本轮已输出的结论。输出：

```
### {角色名} 评审意见

**总体评价**：{一句话}

| # | 问题位置 | 问题描述 | 严重程度 | 优化建议 |
|---|---------|---------|---------|---------|

严重程度：🔴 阻塞（必须修改）/ 🟡 建议（推荐修改）/ 🟢 提示（可选优化）
```

评审维度：
- 是否合理：功能定位、职责划分是否合理
- 是否有优化空间：流程、结构、表述是否可以更好

#### 第二轮：交叉评审

每个角色对**其他角色**的第一轮建议进行评审，侧重：

- **是否合理**：该建议是否基于正确的理解
- **是否必要**：改动带来的收益是否大于引入的复杂度
- **是否冲突**：与其他角色的建议是否矛盾

输出格式：

```
### {角色 A} 对 {角色 B} 建议的评审

| # | 原建议编号 | 判定 | 理由 |
|---|-----------|------|------|

判定：✅ 认同 / ⚠️ 部分认同（需调整）/ ❌ 不认同
```

#### 第三轮：自我修正

每个角色综合其他人对自己建议的评审意见，重新审视自己的建议：

- 维持：仍然认为必要，说明理由
- 修正：接受他人意见，调整建议内容
- 撤回：认可不必要，撤回该建议

输出格式：

```
### {角色名} 最终建议（修正后）

| # | 原建议 | 最终判定 | 说明 |
|---|--------|---------|------|

最终判定：✅ 维持 / 🔄 修正 / 🗑️ 撤回
```

### Phase 5：输出优化建议

综合评审结果，输出**统一优化建议清单**：

1. 只保留最终"维持"和"修正"的建议
2. 按严重程度排序（🔴 > 🟡 > 🟢）
3. 合并重复/相似建议
4. 每条标注影响范围（涉及哪些 skill 文件）

**多角色时**输出格式：

```
## 优化建议清单

| # | 建议内容 | 严重程度 | 影响 skill | 来源角色 | 共识度 |
|---|---------|---------|-----------|---------|--------|

共识度：多数认同 / 部分认同 / 仅提出者坚持
```

**单角色时**输出格式（省略无意义列）：

```
## 优化建议清单

| # | 建议内容 | 严重程度 | 影响位置 |
|---|---------|---------|---------|
```

向用户展示优化建议清单，确认哪些需要执行。

### Phase 6：执行优化

根据用户确认的优化建议，逐条修改对应 skill 文件。每条修改：
1. 展示修改前后的 diff
2. 应用修改

### Phase 7：逻辑一致性检查

所有修改完成后，对整体 skill 体系做最终一致性扫描。

#### 检查范围规则

- **评审范围为单个 skill**：仅检查该 skill 内部一致性（术语、流程自洽、引用有效性）
- **评审范围为多个 skill 或完整体系**：执行全部跨 skill 检查项

#### 检查项

- **术语一致性**：同一概念在不同 skill 中是否用了不同的名称
- **流程衔接**：skill A 的输出是否与 skill B 期望的输入格式匹配
- **职责边界**：是否存在两个 skill 都声称负责同一件事
- **引用有效性**：skill 间的相互引用是否指向正确的章节/文件
- **约定遵从**：各 skill 是否遵循 conventions 中定义的规则
- **缺失环节**：整体流程中是否有"没有 skill 覆盖"的断点

输出：

```
## 逻辑一致性检查报告

✅ 通过项：{N} 项
⚠️ 发现问题：

| # | 类型 | 描述 | 涉及文件 | 修复建议 |
|---|------|------|---------|---------|
```

如有问题，修复后再次检查，直到全部通过。

## 模式二：评审模式

用于已有 skill 修改后的质量评审，直接从 Phase 4 开始执行。

### 触发方式

- 用户提供待评审的 skill 文件路径（支持单个或多个），可选提供修改说明
- 若用户未指定路径但对话上下文中有明确的 skill 文件（如刚刚生成或修改的），可直接使用该文件，向用户确认后执行

### 执行流程

1. **读取 skill 文件**：读取所有待评审的 skill
2. **角色选择**：按「角色选择交互规范」展示完整角色列表，由用户选择
3. **执行 Phase 4**（根据角色数量自动适用降级策略）
4. **执行 Phase 5**（输出优化建议）
5. **用户确认后执行 Phase 6**（执行优化）
6. **执行 Phase 7**（根据评审范围自动适用检查范围规则）

---

## 全局约束

- **不擅自假设**：不确定的地方询问用户，不自行填充
- **保持风格一致**：生成的 skill 遵循用户已有 skill 的 frontmatter 格式和章节风格
- **渐进式输出**：每个阶段完成后暂停等待用户确认，不一口气全部输出
- **评审独立性**：第一轮评审中，逐角色生成意见，每个角色仅从 skill 原文出发，不引用或参考其他角色已输出的结论
- **尊重用户决策**：优化建议由用户最终确认，不强制执行所有建议
- **上下文管理**：当待评审 skill 超过 5 个或选定角色超过 5 个时，分批执行评审，单批输出量控制在合理范围内（建议不超过 5×5），每批完成后暂停，避免输出过长导致上下文截断
