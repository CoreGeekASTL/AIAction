# 基于接口的功能维度软件要素提取

从存量代码仓的接口出发，按功能聚类并提取软件要素，产出人与 AI 共同消费的功能级架构资产。

分析遵循五步工作流：

1. 明确范围与目的
2. 接口探测（扫描脚本 + IDL/路由清单交叉核对）
3. 接口聚类为功能域
4. 按功能维度提取软件要素（模块划分/接口/关键数据结构/调用关系）
5. 生成功能文档（每个功能一篇 md，归档到 docs/story/）

## 第 1 步：明确范围与目的

- 确认代码仓路径、主要语言、需要排除的目录（生成代码、第三方代码、测试目录是否纳入）。
- 确认分析目的，据此选择深度：
  - **接口盘点/汇报** → 浅（接口清单 + 功能归类）
  - **架构文档/新人上手** → 中（功能要素级：模块、接口、数据结构、调用关系）
  - **AI 代码生成资产/接口治理** → 深（资产级，默认，含调用链路与 AI 编码指南）
- 用户未说明时，默认按"深（资产级）"执行，面向 AI 代码生成产出。

## 第 2 步：接口探测

两条线并行，再交叉核对：

1. **IDL/契约清单**：查找 proto、thrift、OpenAPI/Swagger yaml、graphQL schema 等接口契约文件，提取 service/rpc/path 定义。
2. **代码扫描**：运行内置扫描脚本：

```bash
python3 <skill_dir>/scripts/scan_interfaces.py <repo_path> -o scan_result.md
# 可选：--lang go|java|cpp|python 限定语言；--format json 输出结构化结果
```

3. **查漏**：对照 references/interface-catalog.md 的四类接口逐项核对——IDL 契约里有但代码扫描没命中（或反之）的必须追查；特别注意目录中列出的"易遗漏项"（IDL 生成代码虚增、内部接口与外部接口混杂、同接口多实现、消息/事件订阅接口未走显式定义）。区分**外部接口**（对本仓外部暴露）与**内部接口**（仓内模块间契约），外部接口优先分析。

## 第 3 步：接口聚类为功能域

将探测到的接口按功能聚类，遵循"每几个接口对应一类功能"的原则：

- **聚类依据**（按优先级）：IDL 中的 service/模块分组 → 路由路径前缀（如 /api/v1/order/*）→ 包/目录归属 → 共享的关键数据结构 → 业务语义相近。
- 每个功能域命名采用业务语义名（如"用户认证""订单管理""告警订阅"），禁止按技术层命名（如"controller 层"）。
- 控制粒度：一个功能域一般包含 2~10 个接口；超过 10 个考虑拆分，只有 1 个接口且语义独立时允许单独成功能域。
- 产出《功能域清单》：功能名、包含接口、聚类依据，供下一步逐个分析。

## 第 4 步：按功能维度提取软件要素

对每个功能域，提取五类软件要素：

1. **业务叙事（多彩建模）**：按 spec-logic-audit/references/color-modeling.md 的方法论提取——粉色事件链（业务动作时序）、黄色角色（发起者/参与者，区分内外部系统）、绿色实体（被读写对象及状态变更）、蓝色规则（约束/状态机）、术语清单。**防编造红线**：事件/角色/实体/规则只能基于代码可见事实（接口语义、参数、调用链、常量、注释）归纳；业务背景代码中推断不出时标注"代码中未体现"，禁止脑补。
2. **模块划分**：该功能涉及哪些模块/包/类，各自职责，模块间依赖方向。
3. **接口清单**：接口签名（方法名、参数、返回值）、协议与路径、入口文件位置。
4. **关键数据结构**：请求/响应结构、领域模型、存储表结构，字段含义与约束。
5. **调用关系**：从接口入口到存储/外部依赖的调用链路（入口 → 业务逻辑 → 数据访问 → 外部调用），标注关键分支与异步环节。

硬性要求：

- 每个结论必须附代码证据（`文件:行号`），禁止臆测；要素从代码事实归纳，不从注释/文档照抄。
- 接口入口必须精读实现；中间链路按代表性路径跟读，禁止全仓全量阅读。
- 调用关系必须描述到"数据从哪进、到哪出"，含跨模块/跨服务的关键跳转；有条件时用 mermaid 时序图或调用链列表表达。
- 同接口多实现时，列出全部实现及选择机制（配置、依赖注入、策略模式）。

## 第 5 步：生成功能文档（按功能维度归档）

按功能维度拆分输出，**每个功能一篇 md**，统一归档到代码仓 `docs/story/` 目录：

```
<repo>/docs/story/
├── README.md                    # 索引：功能全景清单 + 接口统计 + 文件导航
├── feature-user-auth.md         # 每功能一篇软件要素文档
├── feature-order-manage.md
└── ...
```

文件命名规则：`feature-<功能名>.md`，全小写 kebab-case，功能名用英文短名（如 feature-user-auth.md）。

两个模板均见 references/report-template.md：

1. **索引 README.md**：功能全景清单（每行链接到对应功能 md，含接口数统计）、接口总量与分类统计（外部/内部）、使用说明（AI 编码时如何按功能查阅）。探测到但未纳入任何功能域的接口要单列"未归类接口"一节，证明排查过。
2. **每功能一篇 `feature-<功能名>.md`**：功能概述 + 六节固定结构，按 L1/L2/L3 三层阅读旅程组织，L1 在前——
   - **L1 功能故事（多彩建模，给新人读）**：一张 mermaid 四色建模图呈现业务逻辑（粉=事件主干人话命名、黄=角色含内外部系统边界、绿=实体及状态变更、蓝=规则/约束挂实体），每个粉色事件必须具备触发者/输入/输出/后继四要素；后接术语表（全文业务黑话逐个翻译：术语 | 一句话人话解释 | 出处行号，禁止只写英文全称）。事件名禁止出现文件名/函数名/行号。
   - **L2 结构地图（四节，给深入者与 AI）**：模块划分（mermaid 依赖图+承载功能表）、接口清单（五列表格+语言级接口小表）、关键数据结构（表格只列关键字段）、调用关系（mermaid 时序图+短句补分支）。
   - **L3 AI 编码指南**：只列实现要点，每条 ≤30 字并附证据锚点，1-5 条，禁止空泛表述。

更新策略：docs/story/ 已存在时，按功能逐篇对比更新（功能已下线则标注"已下线"），不要整目录覆盖重写；README.md 索引随功能增删同步更新。

## 质量检查清单

交付前逐项确认：

- [ ] 四类接口（IDL 契约、框架路由、语言接口、消息/事件订阅）全部排查过
- [ ] IDL 契约与代码实现已交叉核对，生成代码未虚增接口统计
- [ ] 外部接口与内部接口已区分，外部接口全部归入功能域
- [ ] 每个功能一篇 md，全部归档在 `docs/story/`，命名符合 `feature-<功能名>.md`
- [ ] README.md 索引中每个清单条目都能链接到存在的功能 md，无死链；未归类接口已单列说明
- [ ] 每篇 md 的 L1 功能故事含 mermaid 四色建模图，每个粉色事件 触发者/输入/输出/后继 四要素齐全
- [ ] 粉色事件名为人话业务动作，图中无文件名/函数名/行号；代码推断不出的背景标注"代码中未体现"而非脑补
- [ ] 术语表覆盖全文业务黑话，每条为一句话人话解释并带出处行号（非英文全称）
- [ ] 每篇 md 的 L2 四类要素（模块划分/接口/关键数据结构/调用关系）齐全，结论均有 `文件:行号` 证据
- [ ] 模块划分有 mermaid 依赖图 + 模块承载功能表；调用关系有 mermaid 时序图，描述到数据进出路径
- [ ] 接口清单与数据结构均为表格，无段落式散文；同接口多实现已列出选择机制
- [ ] 每篇 md 文末 AI 编码指南每条 ≤30 字、附证据锚点、无空泛表述（如"建议合理设计"）
