二、规则与约束（蓝色描述）

规则联合鉴权：IMEI 与 IMSI 必须同时命中才放通出处：§1.2、§2.2.3
规则逃生态：白名单表为空时一律放行出处：§1.4、§4
规则缓存：联合键，容量 1000、超限清最旧 500、TTL 30min、缓存未命中 false 防穿透出处：§2.2.4

约束白名单规格 100W 静态用户；IMEI/IMSI 联合索引出处：§2.6、§7

三、逻辑断裂点与人工裁定

✅ 断点1（数据/规则缺口+术语歧义，阻塞级）已补齐："IMEI 与 IMSI 同时命中"的语义不明——是 (IMEI,IMSI) 组合精确命中同一条记录，还是 IMEI 命中任意一条且 IMSI 命中任意一条（可不同行）？§2.2.3 步骤4 表述为"IMEI 精确命中且 IMSI 精确命中"，§1.4 称"每条记录对应一个 IMEI+IMSI 组合"；§2.4 DAO 仅列 GetByIMEI，未说明 IMSI 如何校验。
人工裁定：组合精确匹配同一行——按 IMEI 查到记录后比对 IMSI 是否一致（对应 DAO 的 GetByIMEI + 内存比对 IMSI），防止 IMEI 与 IMSI 交叉冒用。（2026-07-30）
✅ 断点2（角色缺失+接口信息不明确，阻塞级）已补齐：§3 定义了独立接口 POST /auth/v1/authIMEI，但未说明谁调用它以及它与 4 个链路注入点的关系；请求/响应报文结构未定义；导入接口报文形式未明确。
人工裁定：authIMEI 由 BrowserGW 在会话建立等场景反调 GIDS 鉴权；请求 JSON {"imei":"...","imsi":"..."}，响应 {"code":200/-1}；导入接口用 multipart/form-data 上传 CSV，operation 为 query 参数。（2026-07-30）
✅ 断点3（跨流程数据断裂，阻塞级）已补齐：鉴权依赖请求中的 IMSI 字段，但文档未说明现有终端（26.1 版本）登录/事件请求是否已携带 IMSI。若现网终端不上报 IMSI，白名单一旦导入，所有老终端将因"IMSI 缺失即拒绝"被全量阻断。
人工裁定：27.0 沐恩终端版本配套升级，登录与事件请求新增 IMSI 字段；服务端对缺 IMSI 的老版本请求按"格式非法"拒绝，依靠逃生态保证升级过渡期不阻断。（2026-07-30）
✅ 断点4（异常分支缺失+边界未定义，风险级）已补齐：导入/导出管理接口无任何访问控制——任何能访问 GIDS IP:9090 的人都可调用 update 清表覆盖白名单或导出全量 IMEI/IMSI。
人工裁定：网络隔离——导入/导出接口仅监听 127.0.0.1:9090 或运维内网段，外部不可达；文档明确部署约束，代码不加认证。（2026-07-30）
✅ 断点5（边界条件未定义，风险级）已补齐：CSV 解析边界未定义：①有无 header 行；②文件内 IMEI+IMSI 重复记录如何处理；③"最多 5 个文件"上限系统如何感知与执行；④导入文件名是否强校验。
人工裁定：纯数据 CSV（无 header，所有行当数据读）；文件内重复 IMEI+IMSI 视为校验失败整批拒绝；"5 个文件"仅作为运营约束文档说明，系统不强制；文件名不校验。（2026-07-30）
✅ 断点6（数据/规则缺口，风险级）已补齐：逃生态放行标记按 IMEI+IMSI 联合键缓存，但逃生态是全局状态——导入首批白名单后，已缓存的放行标记在 TTL（最长 30min）内仍放行本应被拒绝的终端，存在切换裸露窗口。
人工裁定：导入接口成功提交事务后，同步调用鉴权服务 ClearCache() 清空内存缓存，白名单立即生效，无裸露窗口。（2026-07-30）
✅ 断点7（验收用例缺失，风险级）已补齐：全文无功能验收用例（用例编号/前置条件/步骤/预期结果）。
人工裁定：在需求文档第 11 章（或附录）引用 testsuit TC_001~005 作为功能验收用例清单，列明每个 TC 覆盖的验收点，不重复写用例步骤。（2026-07-30）
✅ 断点8（实现设计缺时序图，提示级）已补齐：§2.2 功能设计为纯文字+表格，无时序图。
人工裁定：需求文档保持纯文字，时序图由 story-detail-design 阶段在 Story-1~5 详设中补齐（含分支与异常流程）。（2026-07-30）
