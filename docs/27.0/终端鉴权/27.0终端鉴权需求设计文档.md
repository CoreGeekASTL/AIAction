## 1 概述

**【关键内容】**

需求背景：SBG 26.1 版本已经完成基本功能开发和 POC 测试，需要在 27.0 进行商用补齐，本文档针对商用终端鉴权场景进行安全商用补齐。

### 1.1 目的

【关键内容】

本文档主要对终端鉴权场景进行分析设计，明确主要数据结构和主要处理过程，作为今后的编码阶段的输入和编码人员、测试人员的指导。

### 1.2 范围

【关键内容】

- 终端设备鉴权（IMEI + IMSI 联合鉴权）

**特性需求概述**

终端侧访问 GIDS 申请实例时，需要确保该终端在云手机授权范围内；终端申请实例时需要进行鉴权。终端鉴权采用 **IMEI 与 IMSI 联合鉴权**方式，白名单同时存储 IMEI 与 IMSI，鉴权时两者必须同时命中才允许业务放通。

### 1.3 特性需求来源与价值概述

【关键内容】

终端业务访问需要进行鉴权；确保终端业务在云手机授权范围内。

**业务痛点（一线交付反馈）**：

一线交付负责人反馈云手机平台目前处于"裸奔"状态——任何终端、任何 IMEI 都可以直接登录接入云手机实例，系统不做任何准入校验。这带来以下问题：

1. **商业流失**：未购买服务的客户也能白嫖云手机资源，已付费客户的权益无法保障，销售跟客户谈合同的时候没有"抓手"。
2. **资源滥用**：云手机实例数量有限，被未授权用户占用后，真正的付费用户反而抢不到资源，导致客诉。
3. **缺乏管控手段**：运营侧无法按合同/批次精准控制哪些设备可以接入，只能靠人工在网关侧封 IP，效率低且容易误伤。

**价值**：

1. 杜绝白嫖：未授权设备无法接入云手机实例，保障付费客户权益。
2. 资源保供：避免有限云手机实例被未授权用户抢占，降低付费客诉。
3. 精准管控：运营可按合同批次导入/导出白名单，替代网关侧人工封 IP 的低效方式。
4. **双因子防伪**：IMEI 标识设备、IMSI 标识用户身份，联合鉴权可防止单一标识被伪造/冒用，提升准入安全性。

### 1.4 特性场景分析

【关键内容】

#### 方案 1：Radius 信令抄送

**约束：**

1. **固网接入场景**：存在无 radius 角色场景，无法获取套餐，跟 MKT 对齐，固网场景免费使用。
2. 只支持 UP 套餐方式。

**移动场景：**

- **EPSN 侧**：3 人月
  1. 支持从 PCRF 获取用户签约的套餐信息；
  2. EPSN-C 安装云浏览器部分套餐，用户激活后，命中 EPSN-C 本地配置的套餐后，EPSN-C 才携带命中的套餐发给 EPSN-U，EPSN-U 通过 UIS 信令抄送给云浏览器；
  3. Radius Accounting Start 消息中增加扩展字段，携带 PCRF 下发的 CRBN Name(UP)，支持携带多个，最大支持携带 32 个。
  4. 支持抄送多个 Radius Server，如果所有 Radius Accounting Server 均不响应 Radius Accounting 消息，则上报 Radius Accounting Server 故障告警；
  5. 支持用户签约信息的更新，按照全量更新处理。
  6. 1 个扩展字段：策略名称通过分号切割。

- **云浏览器侧**：8.5 人月
  1. 云浏览器支持 Radius Accounting Server 功能，移植 CloudEPSN 的 Radius 模块。（-4 人月）
  2. 云浏览器支持从 Radius Accounting 消息中获取用户签约信息，并存储到本地。单用户最大支持 32 个签约业务名称。（需要增强支持 UDP 的 IP 报文分片重组功能）
  3. 支持用户签约信息的更新。
  4. 云浏览器支持本地配置用户签约的业务名称对应的业务鉴权规则，根据鉴权规则进行业务鉴权处理（GIDS + BrowserGW + MediaCache）。
  5. 如果 CloudEPSN 携带的某个 Service Name 在云浏览器本地未配置，则忽略。

**结论**：该方案需要额外引入 EPSN-C，成本较大上升，且工作量较大；而且目前无一线明确提出要支持鉴权功能，与 MKT（邓云鹏）和架构（侯玉柱）对齐，**不建议采用该方案**。

#### 方案 2：白名单 CSV 导入 + IMEI/IMSI 联合鉴权

采用 CSV 白名单导入方式，运营/后台通过 GIDS REST 接口批量上传/下载白名单，白名单同时存储 IMEI 与 IMSI，鉴权时两者必须同时命中才放通。

- 白名单通过 GIDS 服务 IP 直接提供 REST 接口完成 CSV 上传/下载，无需额外平台适配。
- IMEI 与 IMSI 联合鉴权，双因子防伪，提升准入安全性。
- 逃生态机制：白名单尚未配置（表为空）时放行所有请求，避免线上阻断。

**IMEI 结构说明**：

终端的 IMEI 码为 15 位数字，由 TAC（型号分配码，前 8 位）、FAC（最终装配码，第 9-10 位）、SNR（序列号，第 11-14 位）和 SP（备用位，第 15 位，Luhn 校验）组成。

**沐恩与厂家已确认**：合作厂家同一款型号、同一个工厂、同一批次生产的设备 IMEI 不连续，因此白名单采用逐条精确匹配（每条记录对应一个 IMEI+IMSI 组合），不支持区间匹配。

#### 方案 3：JWT 校验

参照友商及媒体中继的应用业务校验方案。

**JWT 认证流程：**

1. 客户端向网关发起认证请求，携带用户名和密码。
2. 网关转发请求给后端服务。
3. 后端服务验证信息，通过后用私钥生成 Token 返回给网关。
4. 网关返回携带 Token 的应答给客户端，客户端缓存 Token。
5. 客户端向 AI 网关发送业务请求，携带 Token。
6. 网关用公钥验证 Token，通过后透传后端服务。
7. 后端服务处理并应答。
8. 网关返回应答给客户端。

**结论**：该方案需要沐恩公有云侧进行 JWT 发放及公钥发放，需联合开发。与三方对齐，后续版本规划该功能。

#### 各方案对比

- **长期方案**：采用 JWT 方式，且已经与三方达成一致，方案可行。
- **短期方案**：采用方案 2（白名单 CSV 导入 + IMEI/IMSI 联合鉴权 + 逃生态），安全风险需上安全 TMG 汇报。

> **本版本（27.0）落地选型**：采用方案 2，运营/后台直接通过 GIDS 服务 IP 的 REST 接口（`/auth/v1/importIMEIList`、`/auth/v1/exportIMEIList`）实现 CSV 批量上传/下载；白名单同时存储 IMEI 与 IMSI，鉴权时 **IMEI 和 IMSI 联合校验（两者都必须命中）** 才允许业务放通；并增加逃生通道——白名单尚未配置（表为空）时放行所有请求，避免线上阻断。

## 2 特性/功能实现原理

### 2.1 总体方案

白名单管理通过 GIDS 服务 IP 直接提供 REST 接口完成 CSV 上传/下载，鉴权采用 IMEI+IMSI 联合校验。

- **用户列表导入**：运营/后台直接通过 GIDS 服务 IP（端口 9090）POST CSV 文件至 `/auth/v1/importIMEIList`，GIDS 解析校验后批量入库。
- **用户列表导出**：运营直接 GET `/auth/v1/exportIMEIList`，GIDS 查询全量白名单返回 CSV 文本。
- **用户鉴权**：登录链路、事件上报链路注入 IMEI+IMSI 联合鉴权（含逃生态与内存缓存）。

### 2.2 特性功能性设计

### 2.2.1 支持白名单配置导入

- **导入文件名格式**：`SBG_imei_list_inport_0X`（X 为文件导入序号）。
- **文件格式**：只支持 CSV 格式，文件设置只读权限。

**文件内容样例（含 IMEI 与 IMSI）：**

| IMEI | IMSI |
| :--- | :--- |
| 353956070012123 | 460011234567890 |
| 353956070012124 | 460011234567891 |
| 353956070012125 | 460011234567892 |
| 353956070012126 | 460011234567893 |

**校验规则：**

- 单文件导入后解析为强校验，IMEI 和 IMSI 严格只支持 15 位纯数字校验，不允许有其他字符出现（IMEI/IMSI 均为 15 位，对应表结构 `char(15)`）。
- 单个文件建议不超过 20W 用户，可以导入多个文件，最大支持 5 个（共 100W 静态用户规格，DB 规格能否支撑需要实测），对外宣称支持 100W。

**流程机制：**

1. 运营/后台直接通过 GIDS 服务 IP（端口 9090）POST CSV 文件至 `/auth/v1/importIMEIList`，携带参数 `operation=firstImport`（首次导入，要求白名单表为空）或 `operation=update`（覆盖更新）。
2. GIDS 校验文件大小（单文件不超过 3MB）。
3. GIDS 解析 CSV，逐行强校验 IMEI 与 IMSI 为 15 位纯数字。
4. 业务获取用户表格后，对内容做出合法性检查或者用户规格检查（单文件不大于 20W 用户）；检查失败则本次 CSV 文件中的用户全部都不加载，返回错误码。
5. 全部检查通过后，批量加载写入 DB：
   - `firstImport`：要求白名单表为空，否则返回错误（提示使用 update）。
   - `update`：事务清表 + 批量插入，覆盖旧白名单。
6. 返回结果：成功返回 code=200 及导入条数；校验失败返回 code=-1；参数错误返回 code=-2。

### 2.2.2 支持白名单配置导出

- **触发方式**：运营/后台直接 GET `/auth/v1/exportIMEIList`，GIDS 查询全量白名单生成 CSV 文本返回。
- **格式**：同导入样例（CSV，含 IMEI 与 IMSI 两列）。
- **内容**：全量白名单记录（每条为 IMEI+IMSI 精确匹配记录）。

### 2.2.3 用户鉴权（IMEI+IMSI 联合鉴权）

**鉴权方式**：IMEI+IMSI 联合鉴权，白名单同时存储 IMEI 与 IMSI，鉴权时两者必须同时命中才允许业务放通。

**联合鉴权逻辑：**

| 步骤 | 处理 | 说明 |
| :--- | :--- | :--- |
| 1 | 解析终端登录/事件请求中的 IMEI 与 IMSI | 两者均需存在且为 15 位纯数字（格式非法即拒绝，不进入后续匹配） |
| 2 | 逃生态判定：白名单表记录数=0 | 为空则一律放行，不阻断主流程 |
| 3 | 缓存查询 | 以 IMEI+IMSI 联合键查询内存缓存命中结果 |
| 4 | 白名单匹配 | IMEI 精确命中 **且** IMSI 精确命中，两者同时满足 |
| 5 | 鉴权结果 | 均命中→放行；任一未命中→拒绝（登录返回 code=-2，事件返回 code=401） |

### 2.2.4 IMEI/IMSI 鉴权缓存设计

为降低鉴权对 DB 的高频访问、提升登录与事件上报链路性能，并在 DB 短时不可用时提供降级能力，鉴权服务内置内存缓存。

**缓存结构**

| 项 | 取值 | 说明 |
| :--- | :--- | :--- |
| 容器 | `sync.RWMutex` + `map[string]cacheEntry` | Go 标准库，无第三方依赖 |
| 缓存键 | IMEI + IMSI 联合键 | 联合鉴权以 IMEI+IMSI 为粒度 |
| 缓存项 | result（命中 true / 未命中 false / 放行标记）+ expireAt | 同时缓存逃生态放行结果 |
| 容量上限 | 1000 | 超限触发惰性清理 |
| 清理数量 | 500 | 每次清理最旧 500 条 |
| TTL | 30min | 条目过期回源 DB |

**缓存流程**

| 步骤 | 处理 | 说明 |
| :--- | :--- | :--- |
| 1 | 鉴权请求以 IMEI+IMSI 联合键查询缓存（RLock） | 命中且未过期→直接返回，无 DB 调用 |
| 2 | 缓存未命中 | 走逃生态判定 + 白名单匹配（见 2.2.3） |
| 3 | 写缓存（Lock） | 命中→Set(true)，未命中→Set(false) |
| 4 | 惰性清理 | 写入后检查容量超 1000，按 expireAt 升序删除最旧 500 条 |

**并发安全**：读操作用 `RLock`（读多写少，不阻塞 DB），写/清理用 `Lock`；清理在同一 Lock 内完成，无独立 goroutine，无回收风险。

**缓存穿透防护**：未命中 IMEI+IMSI 组合也缓存 `false` 结果（带 TTL），避免不存在组合反复回源 DB。

**缓存失效与更新**：

- **自然失效**：条目存活超 30min 自动失效，下次查询回源 DB。
- **白名单导入更新后**：缓存最长 30min 后反映最新白名单；运营急需即时生效可重启服务（本次不提供主动刷新接口）。
- **逃生态放行标记**：同样写入缓存，避免每次请求都查 Count。

### 2.6 特性下的非功能需求设计

- **性能**：单点鉴权接口（authIMEI）需在白名单表有数据时，单次联合鉴权（IMEI+IMSI）响应满足现有登录链路时延要求；通过内存缓存（联合键命中/未命中/放行标记）降低 DB 访问频次。
- **可靠性/逃生态**：白名单表记录数为 0 时，鉴权服务一律放行，不阻断登录与事件上报主流程，避免线上事故。
- **可维护性**：白名单支持 CSV 批量导入/导出（含 IMEI 与 IMSI 两列），按合同批次管理；导入支持 firstImport（首次）与 update（覆盖更新）两种模式。
- **规格**：白名单表支持 100W 静态用户（每条记录为 IMEI+IMSI 精确匹配组合）。

## 3 外部接口设计

| 接口 | 方法 | 路径 | 说明 |
| :--- | :--- | :--- | :--- |
| 终端联合鉴权 | POST | `/auth/v1/authIMEI` | 校验 IMEI+IMSI 是否同时命中白名单，均命中返回 200，任一未命中返回 401 |
| 白名单导入 | POST | `/auth/v1/importIMEIList` | 直接上传 CSV 批量导入（含 IMEI、IMSI 两列），参数 operation=firstImport/update |
| 白名单导出 | GET | `/auth/v1/exportIMEIList` | 直接下载全量白名单为 CSV（含 IMEI、IMSI 两列） |

> 鉴权注入点（非新增接口，在现有链路中注入）：`gridLoginAuth`、`gridLoginAuthOpenBrowser`、`sendClientEvent`、`sendAppUseTimesEvent`。

## 4 可靠性/可用性/Function Safety 设计

- **逃生态**：白名单表 Count==0 时，鉴权服务对登录与事件上报请求一律放行，保证主流程可用，避免因白名单未配置导致全量阻断。
- **缓存降级**：鉴权结果通过内存缓存（sync.RWMutex + map，以 IMEI+IMSI 联合键）缓存命中/未命中/放行标记，DB 不可用时短时间内可依赖缓存继续鉴权。
- **导入事务性**：CSV 导入采用事务批量写入，校验失败则整批不加载，保证白名单数据一致性。
- **联合鉴权短路**：IMEI 与 IMSI 任一缺失或格式非法即直接拒绝，不进行后续 DB 查询，降低无效负载。

---

## 5 安全/隐私/韧性设计

- **导入文件强校验**：CSV 解析为强校验，IMEI 与 IMSI 严格只支持 15 位纯数字，不允许其他字符；单文件大小受限（3MB）。
- **双因子防伪**：IMEI 标识设备、IMSI 标识用户身份，联合鉴权防止单一标识被伪造/冒用，提升准入安全性。
- **隐私**：白名单仅存储 IMEI/IMSI（设备与用户标识），不存储用户个人敏感信息。

---

## 6 特性非功能性质量属性相关设计

- **可测试性**：DAO 与 Service 层通过接口注入，便于单测 mock；LOCAL_MODE=true 触发 SQLite，支持本地集成测试。
- **可维护性**：遵循 GIDS 现有分层（models/dao/service/controllers/routers），双 DDL（生产 GaussDB + 本地 SQLite）保证两套数据库表结构一致。

## 7 数据结构设计

**白名单数据需求（IMEI + IMSI 联合鉴权）：**

白名单需持久化存储以下数据项，具体表结构由详设阶段定义：

| 数据项 | 约束 | 描述 |
| :--- | :--- | :--- |
| IMEI | 15 位纯数字，需建索引 | 设备标识，精确匹配 |
| IMSI | 15 位纯数字，需建索引 | 用户身份标识（联合鉴权必须字段），精确匹配 |
| 创建时间 | | 记录入库时间 |

**索引需求**：IMEI 与 IMSI 需联合索引，支撑联合鉴权查询性能。
