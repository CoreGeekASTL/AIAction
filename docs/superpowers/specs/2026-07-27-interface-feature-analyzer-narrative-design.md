# interface-feature-analyzer 叙事分层进化设计

> 日期：2026-07-27　状态：已获用户批准　范围：skill 修改 + docs/story/ 存量 8 篇文档补写

## 1. 背景与问题

当前 skill 产出的功能文档（docs/story/*.md）能讲清"代码是什么"（模块/接口/数据结构/调用链，288 处文件:行号证据），但**新人开发读不懂**：

1. 无叙事主线——没有"这功能解决什么业务问题、一个请求经历了什么"
2. 无术语翻译层——IMEI_IMSI、BrowserGW、muen 等业务黑话无解释
3. 无设计意图——只有结构事实，没有业务规则与状态机的人话表达

已确认约束：**首要读者是新人开发**；**功能故事用多彩建模表达业务逻辑**（与 spec-logic-audit 同一份方法论）；L2/L3 现状保留。

## 2. 目标结构：L1/L2/L3 三层阅读旅程

每篇 `feature-<功能名>.md` 改为六节：

```
# <功能名>
> 概述（保留）

## 1. 功能故事（多彩建模）   ← 新增 L1，给新人读
## 2. 模块划分               ┐
## 3. 接口清单                │ L2 结构地图，现状保留
## 4. 关键数据结构            │
## 5. 调用关系               ┘
## 6. AI 编码指南             ← L3，现状保留
```

## 3. L1 功能故事规范

### 3.1 多彩建模图（mermaid 四色）

复用 `.claude/skills/spec-logic-audit/references/color-modeling.md` 的方法论（只引用不复制）：

| 颜色 | 类别 | 本文档中的用法 |
|---|---|---|
| 粉 | 时刻/事件 | 业务动作主干，按时序/因果连接；事件名用人话（如"登录鉴权""分配实例"），禁止函数名/文件名 |
| 黄 | 角色 | 事件发起者/参与者，区分内部系统/外部系统边界 |
| 绿 | 实体 | 事件读写的业务对象，标注操作类型与状态变更（如 UserBind：无→生效→过期） |
| 蓝 | 描述/规则 | 挂在实体上的约束与状态机（如"绑定有效期 3 分钟""主键=IMEI_IMSI"） |

mermaid 用 flowchart + classDef 四色着色（粉 #ffd1dc / 黄 #fff3b0 / 绿 #c8e6c9 / 蓝 #bbdefb）。

**完整性校验**：每个粉色事件必须具备 触发者(黄)/输入(绿/蓝)/输出(绿)/后继(粉)，缺一不可。

### 3.2 术语表

- 覆盖功能故事与接口清单中出现的全部业务缩写/黑话/外部系统名
- 格式：术语 | 一句话人话解释 | 出处（文件:行号）
- 禁止只写英文全称了事（反例："IMEI: International Mobile Equipment Identity"；正例："设备唯一标识，与 IMSI 拼成用户主键"）

### 3.3 防编造红线

事件/角色/实体/规则只能基于代码可见事实归纳（接口语义、参数、调用链、注释、常量）；业务背景代码中推断不出时标注"代码中未体现"，禁止脑补。

## 5. 存量文档处理

8 篇 `docs/story/feature-*.md` 只在开头插入第 1 节（功能故事+术语表），原五节顺延为 2~6 节，内容不动。分派 8 个并行子智能体（resume 原分析智能体，复用其代码事实上下文），各自补写本域 L1 层。

## 6. 验收标准

1. 8 篇文档第 1 节均含 mermaid 四色图（classDef 四色齐全）与术语表
2. 每个粉色事件四要素齐全（抽查每个事件有入有出）
3. 图中无 `.go`、行号、函数名（grep 校验）
4. 术语表条目均带出处行号；出现"代码中未体现"标注视为合规而非缺陷
5. 新人测试：任选一篇，只读第 1 节能复述该功能"谁触发、经过什么、产出什么"
